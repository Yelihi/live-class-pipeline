사용자가 "T-XX 진행" 또는 태스크 구현을 요청하면 이 워크플로우를 따른다.

## 플래그

`--pr` 플래그가 붙은 경우 (예: "T-03 진행 --pr"):
- 구현 전 `feat/t{번호}-{설명}` 형식의 새 브랜치를 생성한다.
- 구현·커밋 완료 후 해당 브랜치를 push하고 PR을 생성한다.
- PR 제목: `feat: T-{번호} {이슈 제목 요약}`
- PR 본문: Summary(구현 내용 3줄 이내), Test plan(검증 명령어), `Closes #N`

`--pr` 없이 요청하면 기존대로 main에 직접 커밋·push한다.

---

## Phase 1 — 이슈 파악

GitHub 이슈를 읽고 완료 기준(Acceptance Criteria)을 정리한다.
완료 기준이 모호하거나 범위가 불명확하면 이 단계에서 사용자에게 먼저 질문한다.

---

## Phase 2 — 병렬 분석

**[시니어 개발자]** 구현 방향 설계
- 생성/수정할 파일과 내용
- 핵심 기술 결정 (element 선택, 스크립트 구조, 패턴 등)
- 코드 품질 기준 (shebang, set -euo pipefail, 주석 정책, 파일명 컨벤션)

**[아키텍쳐]** 설계 검증
- 프로젝트 구조·파일명 컨벤션과의 일관성
- 사용 패키지/라이브러리 버전 및 Ubuntu 22.04 호환성
- 기존 스크립트·설정과의 충돌 여부

---

## Phase 3 — 리뷰어 보완

Phase 2 결과를 종합하여 최종 구현 사양 확정:
- 누락된 엣지 케이스 또는 오류 가능성
- 보안·성능·유지보수성 관점 검토
- Phase 2 수정사항 반영 후 최종 사양 명시
- **구현 완료 후 실제 동작 검증 명령어를 반드시 제시하고 그 결과를 확인한다**

설계 재검토가 필요한 수준의 문제가 발견되면 사용자에게 질문하고 진행한다.

---

## Phase 4 — 병렬 준비

**[테스터]** (비즈니스 로직이 있는 경우에만)
- 핵심 검증 시나리오 목록
- smoke test 명령어 또는 테스트 코드
- 구현 완료 후 해당 명령어를 실제로 실행하여 통과 여부 확인

**[참고 문헌 작성자]**
- 구현에 활용한 공식 문서, man page, 패키지 README URL
- 핵심 개념 출처 (어느 문서의 어느 섹션)

---

## Phase 5 — 구현 및 검증

1. 확정된 사양으로 파일 생성/수정
2. **테스터가 제시한 smoke test 명령어를 실행하여 실제 동작 확인** (실행 불가 환경이면 명시)
3. 검증 통과 후 git commit → push (또는 PR 생성)
4. 이슈 클로즈 (Closes #N)

---

## 질문 트리거

아래 상황에서는 반드시 구현 전에 사용자에게 질문한다:
- 완료 기준이 모호하거나 범위가 불명확할 때
- 설계 방향이 두 가지 이상으로 갈릴 때
- 리뷰어가 설계 재검토를 지적할 때
- 라이브러리·도구 선택이 필요할 때
